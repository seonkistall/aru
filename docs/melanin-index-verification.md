# The melanin index, and every number `ml/skin_indices.py` quotes from outside

2026-09-20 (autopilot cycle 21).

`ml/skin_indices.py` opens with a 20-line benchmark summary — 24 figures about how much
of a skin colour reading is the phone rather than the skin — and the whole design of the
index registry rests on it. Nothing had ever checked those figures against the work they
come from. This does, because the registry decision made in the same cycle (moving
`melanin_index` out of `FEATURE_KEY` into `DERIVED_FROM`) turns on what the melanin index
actually is, and it would be poor practice to settle that from the same docstring whose
accuracy was the thing in question.

**All 24 matched. No number in this repository had to move.**

## 1. What was fetched, and what a reader can re-fetch

`raw.githubusercontent.com` answers on this network (`github.com`'s HTML pages do not —
`http=403`), so the source repository's files can be read directly. The module names its
source as "AI-Hub 028; https://github.com/hpicsk/regional-ccm, manuscript
srt_submission/main.tex and the auto-generated parameters.tex".


`parameters.tex` is the right file to check against: its own header says
`%%% AUTO-GENERATED by src/build_parameters.py. %%% Source: results/*.json`, so every
macro in it is a number the analysis produced rather than a number an author typed into
prose. Each figure below is compared against the macro that states it.

**What this is and is not.** This is a check against the authors' own code and generated
parameters, which is the strongest thing reachable from here. It is not a check against
a published paper, and it cannot detect an error that is in the source analysis itself.
Papers stay unreachable — `doi.org` and `www.ncbi.nlm.nih.gov` both returned `http=000`
when re-probed on 2026-09-20, which is this network's refusal seen through curl.

## 3. The melanin index itself

The registry's `melanin_index` is `100 * log10(100 / max(lstar, 1.0))`, declared
"Takiwaki's melanin index on the CIELAB substitution".

The source's `src/clinical.py:compute_melanin_index` is:

```python
    if method == 'lab':
        # Numerical guard; see MI_L_STAR_FLOOR docstring at module top.
        L_clipped = np.clip(L_star, MI_L_STAR_FLOOR, 100.0)
        return 100.0 * np.log10(100.0 / L_clipped)
```

with `MI_L_STAR_FLOOR = 1.0` and the docstring "Melanin Index = 100 × log10(100 / L\*),
L\*-adapted form of the Takiwaki melanin index".

So the expression matches, the attribution matches, and the low guard matches ARU's
`max(lstar, 1.0)` exactly. **One deviation:** the source clips at BOTH ends and ARU only
at the bottom, so above L\* = 100 the source returns `0.0` and ARU returns a negative
number. It is unreachable from a photo, and that was measured rather than assumed — every
one of the 16,777,216 8-bit sRGB triples through `ml/ita.py:rgb_to_lab`:

```
triples swept: 16777216
max L* over the 8-bit sRGB cube = 100.0 at rgb=(255, 255, 255)
melanin_index at that L*        = 0.0
melanin_index(100.0)            = 0.0
melanin_index(120.0)            = -7.918124604762482  (reference clips to 0.0)
melanin_index(70.0)             = 15.490195998574317  vs toneLstar 70
```

The upper clip is deliberately NOT copied. Clamping would make L\* = 100 and a
physically impossible L\* = 120 report as the same skin, which is worse than a negative
number that can only arrive from a caller that is already wrong.

### Which is why `melanin_index` left `FEATURE_KEY`

The last line above is the registry defect the backlog recorded on 2026-09-19:
`FEATURE_KEY` declared `melanin_index` to be `toneLstar`, `FEATURE_KEY`'s contract is
"the feature key `lib/skin.ts` writes into every exported sample", and at L\* = 70 the
index is **15.49** while the declared column holds **70**.

The item said the fix was a decision, not an edit: either the app computes and exports a
melanin index, or the registry records that the index is derived offline. The source
settles it. The benchmark that ARU cites for the melanin index's own reliability computes
it from a CIELAB L\* reading, the same way — it is a quantity derived from a lightness
measurement, not a separate thing a camera path measures. Adding an app-side field would
create an export column with no producer and no reader; `melanin_index()` has no caller
in this repository outside `ml/selftest.py`.

So `FEATURE_KEY` keeps the six indices the app carries, and `DERIVED_FROM` carries the
one that is computed from a column rather than held in one. `ml/selftest.py` fails if an
index is in neither map or in both, and if a derived index ever equals its source on the
readings the product produces; `tests/skin-index-contract.test.ts` fails if a derived
index's source is not a real `SkinRawFeatures` field.

## 4. A second finding: the ITA band cutpoints were credited to the wrong paper in two files

ARU describes the same five ITA edges (55 / 41 / 28 / 10 / −30) in three places, and it
credited them to two different sources:

| file | what it said before 2026-09-20 |
|---|---|
| `ml/subgroups.py` | "bands follow the Chardon convention"; "#: Chardon ITA bands" |
| `lib/tone-bands.ts` | "Bands are Chardon's" |
| `ml/skin_indices.py` | "Del Bino & Bernerd cutpoints" |

The source separates the two citations cleanly, and the split is the ordinary one — a
1991 paper defines the angle, a 2013 paper cuts it into categories:

- `compute_individual_typology_angle`, on the FORMULA: *"Reference: Chardon et al.
  (1991), Del Bino et al. (2006)."*
- the `ITA_BIN_EDGES` comment, on the CUTPOINTS: *"ITA → six-category skin type
  cutpoints (degrees), per Del Bino & Bernerd (2013)"*, with the same
  `(-30.0, 10.0, 28.0, 41.0, 55.0)` ARU uses.
- `classify_ita`, again: *"the Del Bino & Bernerd (2013) six-category scheme"*.

`ml/subgroups.py` and `lib/tone-bands.ts` now say Del Bino & Bernerd for the edges and
name Chardon for the formula, which is what `ml/skin_indices.py` already said.

**This does not close the backlog item.** That item asks for a primary source for the
cutpoints, and another project's source file is not one. What changed is that three files
in this repository no longer disagree with each other about who to cite. The item stays
open, with the network refusal above as its reason.

## 5. A third finding, recorded and deliberately not acted on

The source guards ITA against a zero `b*` differently from ARU:

```python
ITA_B_STAR_EPSILON = 1e-6
b_safe = np.where(np.abs(b_star) < ITA_B_STAR_EPSILON,
                  ITA_B_STAR_EPSILON * np.sign(b_star + 1e-10), b_star)
```

so an exact zero becomes `+1e-6` and the angle collapses to `+90°` whatever L\* is. ARU
settled its own guard the day before (`docs/ita-guard-decision.md`): `bstar == 0` in all
three implementations, returning `L* > 50 ? 90 : -90`.

The two conventions disagree only at `b* == 0` and only in sign below L\* = 50. ARU's is
not changed to match, and the reason is the measurement cycle 20 already made: a window
guard on `|b*|` puts 242 of the 256 8-bit greys inside it and returns the wrong sign for
241 of them. The source's window is `1e-6`, which cycle 20 measured as containing 1 of
256 — so it is the narrow guard, not the wide one, and ARU's `== 0` is narrower still.
At exactly zero the value is a convention either way, and ARU's is documented as one.
Recorded here so a future cycle comparing the two does not read the difference as a
defect in one of them.
